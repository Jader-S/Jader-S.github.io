> 2026 年 8 月 4 日，脚手架刚搭起来，我还没写几行业务代码，先花时间把视觉、产品、代码三层的决定写死。听起来有点急，但 3D 项目最怕的就是「边做边定风格」——等页面多起来再回头统一，成本会翻好几倍。

ASTRA 是我给自己做的作品站：暗黑太空、霓虹 HUD、一片可以点进去的 3D 星图。这类炫技站很容易长成一个散装特效合集，所以动手之前我先回答了三个问题：**给谁看、长什么样、代码红线在哪。**

## 产品层：先划清楚「不做什么」

受众很明确：这是作品集，不是内容平台。第一印象的冲击力比信息密度重要，广度比单点深度重要；中英双语，面向技术社区可读。相应的非目标也写死了——不做博客平台、不做 CMS、不做电商社交。这条边界后来帮我挡掉过好几次「顺手加个功能」的冲动。

MVP 我压得很小：星图、飞行转场和内容页先跑通，外加**一个**标杆 Demo。博客全量、双语全量、后台、三类 Demo 铺开，统统排到后面。

标杆 Demo 选哪个，我纠结过。最后没选最炫的文生图或 Shader 特效，而是选了「工作难点优化前后对比」——具体来说是我在施耐德做 POI ConfigTools 性能治理的那段：配电树构建从 72 秒压到 2.1 秒（34×），页面跳转 14 秒到 1.2 秒（12×），把低端工控机的 OOM 治住（JS Heap 一度冲到 4197MB）。理由很实在：作品集要证明的是「我能解决什么问题」，不是「我会几个特效」。一个能点开、能看懂前后差距的对比，比一段粒子动画有说服力得多。

叙事线索也在这时候定了：星图上分布着几颗对应人生阶段的星球，沿途三个路标分别对应航天产线、智慧办公、智慧配电，最后收束到 AI 工程化。视觉冲击是外壳，这条线索才是让人愿意往下点的原因。但我特意把它跟技术实现拆开——先把星图和内容页跑通，文案后叠加，两边不互相阻塞。

## 视觉层：所有颜色只在一处定义

这么做不只是为了整齐：切换画质档或主题时只改变量，所有面板、图表、HUD 自动跟随。后面做数据大屏时，ECharts 也是直接读这组变量上色，完全没有第二套配色要维护。

HUD 我拆成几个可复用件：舷窗边框（四角 L 形角标 + 内发光）、坐标读数、缓慢扫过的扫描线、角标仪表、标题的轻微 glitch。星球的五种交互态（idle / hover / 飞行中 / 已访问 / 未解锁）也一次定完，Tab 可达、Enter 触发飞行、焦点环统一用主霓虹色。

两件容易被忽略、但我觉得必须写进规范的事：

**设备分级与降级。** 按宽度分旗舰桌面 / 桌面 / 平板 / 手机四档，逐级降粒子数和 DPR；没有 WebGL2 时直接渲染一张静态的 2D 霓虹舷窗页，星球列表和文字导航照常，路由和内容完全一致，只换表现层。渐进增强的原则是：3D 挂了，功能不能跟着挂，所有 3D 入口在 HUD 侧都有等价入口。

**无障碍基线。** 可点元素 ≥44×44px、对比度 ≥4.5:1、`prefers-reduced-motion` 覆盖所有新增动画。这里有个坑值得单说：相机用的是 GSAP 动画，CSS 媒体查询根本管不到它，只能在 JS 侧读 `detectReducedMotion()` 主动置位。写规范时把这条标出来，比后面补要省事。

## 代码层：几个反复权衡后的决定

架构上我尽量克制，能不引的依赖不引：

- **飞行状态机**用轻量枚举 + Zustand，没上 XState。状态就五个：`IDLE → FLYING_IN → VIEWING → FLYING_OUT → IDLE`，动画用 GSAP timeline，状态切换由 `onComplete` 回调驱动。这点复杂度自己写反而更可控。
- **三层 Error Boundary**：`<Canvas>` 外层崩了降级到 2D 舷窗；每个懒加载 Demo 各自包一层；Sandpack 编辑器再单独包一层。3D 和在线编辑器都是「容易炸但炸了不该拖垮整页」的东西。
- **3D 资产程序化优先**：星球用 `icosahedronGeometry` 加自定义材质，不依赖外部模型；确实要模型的火箭才走 GLTF + Draco，纹理转 WebP。
- **首屏预算**卡在 250KB（gzip），3D 和 Demo 一律懒加载，配一个霓虹转圈的「校准中」过渡。
- **严格 TS**，`strict: true`，禁 `any`。

博客这一块我选了 MDX：`@mdx-js/rollup` + frontmatter 插件，构建期用 `import.meta.glob` 懒加载扫描文章，否掉了需要 SSR 的 `next-mdx-remote`（这是个 SPA，不值得为几篇文章引入服务端）。

## 顺带踩到的一个坑：MDX 不是 Markdown

真把文章往里灌的时候才发现，这套管线比想象中挑剔，值得记一笔。

第一，**没装 `remark-gfm`，表格根本不解析**。markdown 里好好写的 `| a | b |`，渲染出来就是一段带竖线的纯文本。第二，更要命的，MDX 会把正文里裸的 `<Html>`、`{a,p,q}` 当成 JSX 标签和表达式去**编译**，技术文章里到处是这种片段，轻则渲染异常，重则直接编译失败。第三，frontmatter 里的 `date` 如果写成裸的 `2026-08-04`，YAML 会解析成 Date 对象，列表按 `date.localeCompare()` 排序时直接抛错——必须加引号变成字符串。

我的处理是加了一道构建预处理：文章仍然用普通 markdown 写，发布前由脚本把表格转成原生 `<table>`、把非代码段里的 `{ } <` 转成 HTML 实体、把 frontmatter 规范化，再输出成 MDX。源文和发布版分开，改完源重跑一次就行，不用手工维护两份。反引号代码段和围栏代码块原样保留——它们在 MDX 里本来就是纯文本，不参与解析。

还有一条更基础的教训：**给站点加内容之前，先去看消费方到底读哪个目录、哪种格式、要哪些字段**，再决定文件往哪放。我一开始按常识建了个 `logs/` 目录写文章，结果列表页只扫 `src/content/blog/*.mdx`，写了半天页面上一篇文章都没有。这件事本身不高级，但每次换项目都容易再犯一次。

## 这套规矩值在哪

写完这些，后面几个月加 Demo、加页面、改交互，几乎没再为「这个按钮该用什么颜色」「这个状态放哪层」重新做决定。规范真正的价值不是约束，是**把决策成本一次性付掉**。

当然也有代价：3D 那块 chunk 一直偏大，首屏预算迟早要正面处理；有些条目（比如视觉截图对比测试）我到现在也没强制起来，3D 场景太难稳定复现。规范是活的，写下来是为了有据可依地改，不是供着。
