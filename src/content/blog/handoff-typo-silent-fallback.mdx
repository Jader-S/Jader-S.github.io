> 2026 年 10 月 28 日，我在 `langchain-deepagent` 里调 handoff，撞上一个特别会骗人的 bug：当轮日志明明白白写着「控制权已移交 coding_agent」，下一轮用户一开口，图又跑回默认的 `web_agent`。不报错、不抛栈、类型检查全过。

## 现象

用 `transfer_to` 把控制权交给 `coding_agent`，当前轮看起来完全成功，有 ToolMessage 说移交完成。但从 `START` 再进图时，条件边每次都回落到 `web_agent`。状态里「以为」写过 `active_agent`，读的时候却像从没存在过。

## 问题代码

写入用的是正确字段名：

```python
# src/langchain_python/tools/transfer_to.py（节选）

return Command(
    graph=Command.PARENT,
    goto=agent_name,
    update={
        "active_agent": agent_name,
        "messages": [*all_messages, tool_messsage],
    },
)
```

状态类型声明也对：

```python
class GraphState(AgentState):
    active_agent: NotRequired[str]
```

但条件边读的是**拼错的键**：

```python
# src/langchain_python/agents/handoff.py（问题所在）

flow.add_conditional_edges(
    START,
    lambda state: state.get("acitve_agent", "web_agent"),  # ← 少了一个字母、还换了位
    ["web_agent", "coding_agent"],
)
```

`acitve_agent` 永远拿不到值，于是每一轮从 `START` 都走默认值。

同文件里还埋着一个相关坑：消息裁剪时只取最后一条，会把本轮的工具调用过程丢掉。正确做法是整段带上再追加 ToolMessage：

```python
# 错误：只留最后一条，丢掉本轮工具过程
# ai_message = runtime.state.get("messages", [])[-1]

# 正确
all_messages = runtime.state.get("messages", [])
```

## 根因

Handoff 靠**父图状态字段**记住「当前该跑哪个子 Agent」。写入键和读取键必须字节级一致，这是一对契约。

这类 bug 难查在三点：类型检查不会报错，`state.get` 对任意字符串 key 都合法；运行时也不抛异常，只是静默走默认分支；日志里还能看到「移交成功」的 ToolMessage，等于给了你一个错误的安慰。我一开始怀疑的是 `Command.PARENT` 的语义、子图状态合并、甚至框架版本，绕了一大圈才回去数那几个字母。

## 正确写法

```python
flow.add_conditional_edges(
    START,
    lambda state: state.get("active_agent", "web_agent"),  # 与 update 键一致
    ["web_agent", "coding_agent"],
)
```

我给自己留了张自检清单：

1. `Command.update` 的键 == 条件边 `state.get` 的键 == `GraphState` 字段名。
2. 用一次真实**多轮**对话验证：移交后第二轮用户消息是否仍停在目标 Agent。单轮成功不算数。
3. 打印 `state.keys()` / `state.get("active_agent")`，确认不是 `None`。

顺带一提，整理这篇的时候仓库里 `handoff.py` 还留着 `acitve_agent` 这个拼写，本地修掉再发版更稳。

## 可复用结论

多智能体路由里，**「写状态」和「读状态」是一对契约**。拼写错误不会炸栈，只会表现为「怎么教都记不住该谁干」。

遇到「移交成功但下次又重置」，先对键名做精确字符串比对，再怀疑框架。这个顺序能省下我那天下午的两小时。
